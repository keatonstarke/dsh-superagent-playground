## 0. 结论摘要

| 维度 | 结论 |
| --- | --- |
| 主流路径 | 官方 API 免费层 → Gemini CLI OAuth → Antigravity（反重力）本地服务 → Web 端 Cookie 反代 → 第三方共享池 |
| 性价比最高 | CLI / Antigravity 两条 OAuth 路线：额度大、协议稳定、无 Cookie 失效问题 |
| 最脆弱 | Web 端 Cookie 反代：`__Secure-1PSID` 生命周期短，风控联动强，解析层随前端改版失效 |
| 单号日产 | CLI 路线约 1000 req/号/日；Antigravity 按 5 小时窗口滚动配额；Web 反代取决于账号等级，量级 100~500 req/日 |
| 号源成本 | 自建注册 ¥1~6/号（含接码 + 代理摊销），成品号 ¥2~15/号，企业/教育域名号 ¥20~80/号 |
| 号池日损耗 | 5%~20%，风控窗口期可到 40% |
| 反代失效周期 | 上游协议/前端改版导致 2~8 周一次必须适配 |
| 盈亏平衡 | 单价维度便宜 40 倍以上（对 gemini-3-pro），但计入号损/代理/人力后综合 TCO 优势收敛到 6~8 倍 |
| 选型建议 | 自用规模 < 50 万 token/日：直接买官方；50 万~5000 万 token/日：CLI/Antigravity 反代 + 小号池；再往上必须做多路上游 + 降级到官方付费 |

一句话：**"白嫖"的真实成本不在账号，而在协议适配、号池保鲜和失效应急。**

## 1. 术语与边界

| 术语 | 含义 | 备注 |
| --- | --- | --- |
| 反重力 | Google Antigravity（agent-first IDE / 客户端），内置 Gemini 3 Pro、Claude Sonnet 等模型额度，免费层可被本地反代导出成 API | 名字来源于 Antigravity，社区简称"反重力" |
| 反代 | 把某客户端（CLI / IDE / Web）的私有协议翻译成 OpenAI / Anthropic 兼容 API 的中间层 | 分"协议反代"和"账号反代"两类 |
| 号源 | 可用账号的供给渠道：自建、成品号、Cookie/Token 池、共享池 | 质量差异极大 |
| 注册机 | 批量注册 + 养号 + 提取凭证的自动化流水线 | 成败取决于指纹、IP、号码信誉 |
| 白嫖 | 不支付按 token 计费，用免费额度 / 试用额度 / 客户端配额承载生产流量 | 本质是"配额套利" |

三条正交的分类轴：

1. **凭证类型**：API Key / OAuth Access Token / Web Cookie / 设备码
2. **协议类型**：公开 REST / 私有 v1internal / batchexecute（Web）
3. **额度类型**：按日配额（RPD）/ 滚动窗口配额 / 试用 credit

组合起来决定了一条路径的**上限、稳定性和维护成本**。

## 2. 五条主流路径对比

| 路径 | 凭证 | 协议 | 单号额度 `[估算]` | 稳定性 | 适配成本 | 适用场景 |
| --- | --- | --- | --- | --- | --- | --- |
| A. 官方 API 免费层 | API Key | 公开 REST | flash 250 RPD / flash-lite 1000 RPD；pro 基本无免费 | ★★★★★ | 无 | 小流量、需合规 |
| B. Gemini CLI OAuth | Google 账号 OAuth | 私有 `v1internal` | 60 RPM / 1000 RPD 量级 | ★★★★ | 中（协议稳定，改动少） | 主力路线 |
| C. Antigravity（反重力） | 客户端 OAuth | 本地 language server HTTP | 5 小时滚动窗口，数十~数百 req | ★★★☆ | 中高（版本跟随） | Pro 级模型白嫖 |
| D. Web 端 Cookie 反代 | `__Secure-1PSID` 等 | `batchexecute` / BardChatUi | 100~500 req/日 | ★★ | 高（前端改版即失效） | 兜底、图文 |
| E. 第三方共享池 | 混合 | 混合 | 不可控 | ★☆ | 低 | 一次性、非生产 |

**关键结论**：B 与 C 是同一条技术脉络的两端——两者都是"用客户端身份换额度"，只是 C 的额度来自更贵的模型池，B 的额度来自更宽的日配额。工程上应把 B/C 抽象成同一个 `upstream provider` 接口，D 只做兜底。

## 3. 反重力（Antigravity）深挖

### 3.1 为什么它能白嫖

Antigravity 的计费口径是**客户端订阅/免费层额度**，不是 AI Studio 的 token 计费。客户端把模型调用打到自己的后端（`cloudcode-pa` 一类服务），后端按"用户 + 产品 + 窗口"发放配额。于是：

- 同一账号在两个产品下有两套独立配额（CLI 一套、IDE 一套）
- 只要请求带着合法客户端身份（OAuth token + 产品标识 + project 字段），后端就按客户端配额结算
- 官方不会校验"请求是否真的来自 IDE UI"

这就是所有反重力反代的共同前提。

### 3.2 请求形态（示意，字段名以实际抓包为准）

```http
POST https://<ANTIGRAVITY_HOST>/v1internal:streamGenerateContent?alt=sse
Authorization: Bearer <OAUTH_ACCESS_TOKEN>
Content-Type: application/json
User-Agent: <CLIENT_UA>

{
  "model": "gemini-3-pro-high",
  "project": "<CLOUD_PROJECT_ID>",
  "request": {
    "contents": [{"role": "user", "parts": [{"text": "hi"}]}],
    "generationConfig": {"temperature": 0.7, "maxOutputTokens": 8192}
  }
}
```

三个必须字段决定了成功率：

| 字段 | 来源 | 失效表现 |
| --- | --- | --- |
| `Authorization` | OAuth refresh → access token（约 1 小时） | 401 `UNAUTHENTICATED` |
| `project` | 首次调用时后端分配的 project id，通常需缓存 | 400 `FAILED_PRECONDITION` |
| `User-Agent` / 客户端版本 | 与 token 的 client_id 匹配 | 403 / 空响应 |

### 3.3 客户端本地服务抽取路线

Antigravity 启动后会在本机拉起 language server 并监听随机高位端口，同时把 access token 落在本地配置/日志中。抽取流程：

1. 启动客户端，`ps` / `lsof -iTCP -sTCP:LISTEN -p <pid>` 定位监听端口
2. 从配置目录（macOS `~/Library/Application Support/...`、Linux `~/.config/...`、Windows `%APPDATA%\...`）取 OAuth 凭证与 project id
3. 用 `curl` 直打本地端口验证：能返回 SSE 即协议通
4. 反向代理层复用同一份凭证，按窗口配额做调度（额度用尽 → 换号，不是重试）

注意两个工程细节：

- 本地端口与内部路径随版本变动，**必须做能力探测**（探到 404 就走下一候选路径），不要硬编码
- 客户端会周期性刷新 token，反代层要么读同一份凭证文件，要么自己走 refresh flow；两条路并存时注意竞态（refresh token 轮换会让旧 token 失效）

### 3.4 反重力 vs CLI 的取舍

| 项 | Antigravity | Gemini CLI |
| --- | --- | --- |
| 模型档位 | Gemini 3 Pro / Claude 系（更高） | Flash / Pro（受限） |
| 配额形态 | 5 小时滚动窗口 | 日配额 + 分钟限速 |
| 协议稳定性 | 中（客户端更新频繁） | 高 |
| 单请求成本 | 低（高档模型免费） | 低 |
| 适合 | 质量敏感、并发不高 | 吞吐敏感、长跑批处理 |

实践组合：**CLI 承接 80% 常规流量，Antigravity 承接高档模型请求，Web 反代只在两者全挂时兜底**。

## 4. 反代架构

### 4.1 参考架构

```
client (OpenAI/Anthropic SDK)
        │
        ▼
┌────────────────────────────────────────────┐
│ gateway                                    │
│  · 鉴权 / 配额 / 计费钩子                    │
│  · 协议转换 (openai ⇄ gemini ⇄ claude)      │
│  · 流式 SSE 透传 · 工具调用映射 · 多模态编码   │
└───────────────┬────────────────────────────┘
                │ 选路（健康度 + 配额 + 成本）
    ┌───────────┼────────────┬─────────────┐
    ▼           ▼            ▼             ▼
 CLI 池     Antigravity 池  Web 池      官方 Key
 (token)     (token)      (cookie)     (付费兜底)
    │           │            │             │
    └───────────┴────────────┴─────────────┘
                │
         ┌──────▼──────┐
         │ 号池状态存储 │  Redis: 额度窗口 / 冷却 / 健康分
         └─────────────┘
```

### 4.2 协议转换要点

| 差异点 | Gemini 侧 | OpenAI 侧 | 处理 |
| --- | --- | --- | --- |
| 角色 | `user` / `model` | `user` / `assistant` / `system` | `system` 提到 `systemInstruction` |
| 流式 | SSE，多个 JSON 数组元素 | `data: {...}` 逐块 | 逐块解码再重组 |
| 工具调用 | `functionCall` / `functionResponse` | `tool_calls` / `role: tool` | 双向映射 + id 生成 |
| 多模态 | `inlineData`（base64） | `image_url` | 下载/转 base64，注意请求体上限 |
| 结束原因 | `finishReason` | `finish_reason` | 枚举映射，`MAX_TOKENS` 常被误判 |
| 用量 | `usageMetadata` | `usage` | 有的上游不返回，需本地估算 |

**踩坑清单**（按出现频率排序）：

1. 流式最后一个 chunk 缺 `usage`，计费钩子崩 → 本地按字符估算兜底
2. `finishReason: MALFORMED_FUNCTION_CALL` 在工具调用场景高频，需要重试而不是透传
3. 长上下文请求体被上游静默截断 → 必须在网关侧做 token 预检
4. SSE 心跳缺失导致中间层 60s 超时断流 → 每 15s 注入注释行 `: ping`
5. 多号轮询时同一会话被打散到不同号，工具调用状态丢失 → 会话粘性（按 `conversation_id` 哈希）

### 4.3 号池调度

健康分模型（0~100）：

```
health = 100
       - 30 * recent_401_rate
       - 25 * recent_429_rate
       - 20 * p95_latency_penalty
       - 15 * quota_exhausted_flag
       + 5  * success_streak_bonus
```

调度策略：

- **加权最小负载 + 配额感知**：优先选"剩余窗口配额 / 当前在飞请求数"最大的号
- **熔断**：连续 3 次 401 → 立即下线并触发凭证刷新；连续 5 次 429 → 进入冷却到窗口重置
- **粘性**：同一 `conversation_id` 在 TTL 内固定到同一号
- **灰度**：新号只接 5% 流量，跑满 20 次成功再提权

```python
# 选路伪代码
def pick(pool, model, conv_id):
    if conv_id in sticky and sticky[conv_id] in pool.alive():
        return sticky[conv_id]
    cands = [a for a in pool.alive()
             if a.supports(model) and a.health >= 60 and a.quota_left() > 0]
    if not cands:
        raise NoUpstream(model)
    return max(cands, key=lambda a: (a.quota_left() / (a.inflight + 1)) * a.health)
```

### 4.4 凭证生命周期

| 凭证 | TTL | 刷新方式 | 失败处理 |
| --- | --- | --- | --- |
| OAuth access token | ~1h | refresh_token 换新 | 刷新失败 → 号标记 `reauth` |
| refresh token | 长期，但会轮换 | 刷新时返回新值，必须落盘 | 未落盘 = 号报废 |
| Web Cookie | 数小时~数天 | 无（需重新登录） | 失效 → 回注册机重登 |
| project id | 长期 | 首次调用分配，缓存 | 400 时重新分配一次 |

> 最常见的"号池一夜掉一半"，80% 是 refresh token 轮换没落盘。

## 5. 号源

### 5.1 类型学

| 类型 | 获取方式 | 单价 `[估算]` | 存活期 | 额度档 | 风险 |
| --- | --- | --- | --- | --- | --- |
| 自建 Gmail | 注册机 + 接码 + 住宅 IP | ¥1~6 | 3~30 天 | 标准 | 注册即封比例高 |
| 成品号（批量） | 号商 | ¥2~15 | 1~20 天 | 标准 | 撞库号、共享号、已被标记 |
| 教育/企业域名 | Workspace 试用、edu 域名 | ¥20~80 | 30~180 天 | 高档 | 域名随时被回收 |
| Cookie 池 | 抓取/共享 | ¥0.5~5/条 | 数小时~3 天 | 看账号 | 极易失效 |
| OAuth token 池 | CLI 登录后导出 | ¥3~20 | 7~60 天 | 标准 | 需要 device flow 过验证 |
| 公共共享池 | 社区项目 | 0 | 分钟级 | 不稳定 | 完全不可控 |

### 5.2 号源质量指标

采购/自建都要按这六项打分，低于阈值的号不要进主池：

| 指标 | 采集方式 | 合格线 |
| --- | --- | --- |
| 注册时长 | 账号元数据 | > 7 天 |
| 首次登录 IP 归属 | 登录日志 | 与当前出口同国家 |
| 手机验证状态 | 试探性接口 | 已验证 |
| 历史调用成功率 | 试跑 10 次 | > 80% |
| 额度是否被共享 | 并发撞车检测 | 无并发冲突 |
| 是否已有风控标记 | 403 比例 | < 10% |

### 5.3 号源寿命的经验规律

- **IP 稳定性 > 账号年龄**：同一住宅 IP 养 3 天的号，比每天换 IP 的 30 天号活得久
- **首次调用节奏**：新号前 24 小时超过 50 req 的，7 日存活率显著下降
- **同 C 段聚集**：同一 /24 下超过 ~20 个号，几乎必然连带封
- **号池规模效应递减**：超过 500 号后，边际收益被调度复杂度吃掉

## 6. 注册机

### 6.1 流水线

```
代理IP池 ──┐
接码平台 ──┼─▶ 会话编排 ─▶ 注册 ─▶ 过验证 ─▶ 养号 ─▶ 凭证提取 ─▶ 入池
指纹浏览器 ─┘                                    │
                                         质量打分 / 淘汰
```

### 6.2 关键组件

| 组件 | 选型 | 说明 |
| --- | --- | --- |
| 浏览器自动化 | Playwright / Patchright / Camoufox | 后两者针对 CDP 特征做补丁 |
| 指纹 | 每号固定一套：UA、时区、语言、Canvas/WebGL、字体、硬件并发 | 同指纹复用 = 关联封 |
| IP | 住宅/移动代理，一号一 IP，粘性会话 | 机房 IP 通过率极低 |
| 号码 | 接码 API，按国家/运营商筛 | 号码信誉是最大瓶颈 |
| 邮箱 | catch-all 域名 + 别名 | 便于批量收验证信 |
| 编排 | 队列 + 状态机，失败重试上限 3 | 重试太多会把 IP 打脏 |

### 6.3 风控对抗要点

| 风控层 | 表现 | 对策 |
| --- | --- | --- |
| TLS/JA3 | 非浏览器指纹直接 403 | 用真实浏览器栈，别用 requests |
| 设备指纹 | 同指纹多号 → 批量封 | 一号一 profile，profile 持久化 |
| 行为节奏 | 表单填写速度异常 | 加人类化延迟、鼠标轨迹、滚动 |
| 号码信誉 | 接码号直接拒 | 换供应商，优先实体卡段 |
| ASN 信誉 | 数据中心 ASN 全拒 | 住宅/移动 ASN |
| 图形验证 | reCAPTCHA 类 | 打码服务 或 语音/无障碍通道；成功率 60~85% |

`[实测]` 社区口径的成功率区间：单次注册 30%~70%，端到端（注册→可调用）20%~50%。也就是说**一个可用号的真实成本 ≈ 单价 / 0.3**。

### 6.4 养号

新号直接投产是最常见的浪费。建议：

1. 第 1 天：登录 + 1~2 次极短请求，间隔数小时
2. 第 2~3 天：每天 5~20 次，模拟正常用户时段
3. 第 4 天起：进入灰度池，接 5% 流量
4. 连续 3 天成功率 > 90% → 进主池

## 7. 成本模型

### 7.1 官方价格基准 `[官方，量级]`

| 模型 | 输入 $/1M | 输出 $/1M |
| --- | --- | --- |
| gemini-2.5-pro（≤200k 上下文） | 1.25 | 10.00 |
| gemini-2.5-flash | 0.30 | 2.50 |
| gemini-2.5-flash-lite | 0.10 | 0.40 |
| gemini-3-pro（高档） | 2.00 | 12.00 |

### 7.2 单号产出

设平均请求 = 3k 输入 + 800 输出 token：

| 路径 | 日请求 | 日 token（输出） | 等效官方成本/日/号 |
| --- | --- | --- | --- |
| CLI（1000 RPD，2.5-flash） | 1000 | 0.8M | $2.9 |
| CLI（1000 RPD，2.5-pro） | 1000 | 0.8M | $11.8 |
| Antigravity（窗口制，估 200 req/5h ≈ 900/日，3-pro） | ~900 | 0.72M | $14.0 |
| Web 反代（300 RPD，2.5-flash） | 300 | 0.24M | $0.9 |

单请求口径：3k 输入 × 单价 + 800 输出 × 单价。
- 2.5-flash：3000×0.30/1M + 800×2.50/1M = **$0.0029**
- 2.5-pro：3000×1.25/1M + 800×10/1M = **$0.01175**
- 3-pro：3000×2.00/1M + 800×12/1M = **$0.0156**

### 7.3 单号持有成本

| 项 | 摊薄方式 | 元/号/日 `[估算]` |
| --- | --- | --- |
| 号本身 | ¥4 / 存活 10 天 / 成功率 0.35 | ~1.14 |
| 住宅代理 | ¥30/GB，单号日耗 20MB | ~0.60 |
| 接码 | ¥1.5 / 次 / 0.4 成功率 | ~0.38 |
| 服务器 + 带宽 | 网关 ¥200/月 ÷ 200 号 | ~0.03 |
| 维护人力 | 0.5 人日/周 ÷ 200 号 | ~0.36 |
| **合计** | | **~2.5 元/号/日** |

### 7.4 折算与盈亏平衡

以 2.5-flash、1000 RPD/号 计，一个号日产出约 $2.9 ≈ ¥21（按 1 USD ≈ 7.2 CNY），持有成本 ¥2.5 → **毛利约 88%**。

换成 3-pro 档（$15.6/号/日 ≈ ¥112），单价维度相当于省 **45 倍**，约 1.6 个数量级。但这是"零人力、零损耗"的乐观口径：置入 §7.3 的代理、接码、号和人力之后，综合 TCO 优势收敛到 **6~8 倍**。

成本结构随规模变化：按 2.5-flash 口径折算（等效官方价 = $2.9 × 号数 × 7.2），TCO = 2.5 元/号/日 + 固定成本（网关带宽 ≈ ¥7/日）+ 人力（0.5 人日/周起，按 ¥800/人日）：

| 规模（号） | 日产出（M output token） | 等效官方价/日 | 白嫖 TCO/日 | 倍数 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 10 | 8 | ¥210 | ¥92 | 2.3× | 规模不经济，不如直接买 |
| 100 | 80 | ¥2 100 | ¥317 | 6.6× | 明显划算，一人可维护 |
| 1 000 | 800 | ¥21 000 | ¥2 900 | 7.2× | 需要专职 + 值班 |
| 5 000+ | 4 000 | ¥105 000 | ¥14 100 | 7.4× | 组织与合规风险 > 成本收益 |

倍数在 100 号以后基本平掉，说明**规模放大买到的是绝对节省，不是单位效率**。

**盈亏平衡点约在 30~50 个稳定号**：低于此，工程复杂度与账号损耗抵消了价格优势。

### 7.5 隐性成本清单（最容易被低估）

1. 协议适配：每次上游改版 1~3 人日
2. 应急值守：封号潮需要小时级响应
3. 观测与告警建设：一次性 3~5 人日
4. 数据合规审查：日志里不能留用户内容，需要额外脱敏
5. 质量损失：号池抖动带来的 5xx/截断，重试成本与体验损失

## 8. 稳定性

### 8.1 分层故障模型

| 层 | 典型故障 | 频率 | 影响面 | 缓解 |
| --- | --- | --- | --- | --- |
| 账号层 | 401/403、验证挑战、批量封 | 高（日级） | 单号 | 号池冗余 ≥ 3 倍 |
| 会话层 | refresh token 轮换丢失、Cookie 过期 | 中（日级） | 单号 | 落盘 + 双写 |
| 协议层 | 字段改名、路径变更、UA 校验 | 中（周~月级） | 全池 | 能力探测 + 多路径 |
| 上游层 | 429、503、区域限制 | 高（小时级） | 部分号 | 退避 + 换号 + 官方兜底 |
| 网关层 | SSE 断流、内存泄漏、连接池耗尽 | 低 | 全站 | 压测 + 心跳 + 限流 |

### 8.2 上游变更史（示意）

`[实测]` 观察到的模式：每次大模型发布或客户端大版本更新，都会伴随 1~2 周的协议抖动（新字段、新校验、旧路径下线）。反代项目在这期间通常一天多个 patch。**结论：把"上游协议版本"当成一个需要主动探测的外部依赖，而不是常量。**

### 8.3 SLO 建议

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 可用性 | 99.0%（自用）/ 99.5%（对外） | 单路上游做不到 99.9 |
| 首 token 延迟 P95 | < 3s | 受上游排队影响大 |
| 请求成功率 | > 97% | 含重试后 |
| 号池健康率 | > 70% | 低于 50% 触发扩容告警 |
| 429 比例 | < 5% | 高于 10% 说明调度或额度估算有问题 |

### 8.4 观测

```yaml
# prometheus 指标建议
- name: gemini_upstream_requests_total
  labels: [provider, model, account_bucket, code]
- name: gemini_upstream_latency_seconds
  labels: [provider, model]        # histogram
- name: gemini_pool_accounts
  labels: [provider, state]        # alive / cooling / reauth / dead
- name: gemini_pool_quota_remaining
  labels: [provider, account_bucket]
- name: gemini_stream_truncated_total
  labels: [provider, reason]
```

告警规则（最小集）：

- `health_rate < 0.5` 持续 10 分钟 → P1
- `code="401"` 5 分钟速率 > 池规模 10% → P1（疑似批量封）
- `stream_truncated / total > 3%` → P2（协议适配问题）
- 单 provider 成功率 < 80% → 自动摘除该 provider

### 8.5 降级链

```
Antigravity ──fail──▶ CLI ──fail──▶ Web ──fail──▶ 官方付费 Key ──fail──▶ 明确报错（不静默重试）
```

降级要带**预算闸门**：付费兜底只允许承接标记为 `critical` 的请求，避免一次封号潮把账单打爆。

```
日均输出 token?
├─ < 20 万        → 官方 API 免费层 / 付费（最省心）
├─ 20 万 ~ 200 万 → CLI 反代 + 10~30 号池（够用且简单）
├─ 200 万 ~ 2000 万
│   ├─ 质量敏感 → Antigravity 主 + CLI 备

└─ > 2000 万      → 多 provider 聚合 + 官方付费兜底 + 专人运维
```

判断"要不要自建"的三个问题：

1. 有没有人能在一小时内响应封号潮？没有 → 别自建
2. 业务能否容忍 1%~3% 的失败与截断？不能 → 别自建
3. 省下的钱是否超过 0.5 人力的成本？不超过 → 别自建

## 11. 风险与工程边界

- **账号风险**：批量注册与共享凭证违反上游服务条款，账号可被随时回收；号池必须按"随时归零"设计（灰度、冗余、付费兜底）
- **数据风险**：走第三方/共享池意味着请求内容经过不受控的中间人；敏感数据必须留在自建链路上
- **供应链风险**：号商、接码、代理都存在"同一批资源被卖给多个买家"的问题，会互相踩踏
- **协议风险**：私有端点没有兼容性承诺，任何一次客户端更新都可能让整条链路失效
- **合规风险**：面向公众提供服务时，转售免费额度通常被明确禁止；对外产品应使用官方付费 Key

工程上可行的姿态：**把白嫖链路定位为"内部研发加速器 / 降级兜底"，不作为对外产品的主链路。**
